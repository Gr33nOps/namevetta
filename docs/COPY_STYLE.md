# Copy style

All user-facing copy — page headings, body text, button labels, error
messages, empty states, evidence descriptions — must read like a small,
competent product team wrote it. Not a marketing agency. Not an AI
assistant that defaults to generic SaaS phrasing.

## The test

Before shipping any new copy, ask: **would an actual person say this if
they only had ten seconds to explain the feature?** If not, cut it or
rewrite it plainer.

A stronger version of the same test: **could this sentence appear
unchanged on 1,000 unrelated SaaS websites?** If yes, it's not saying
anything specific to this product, so delete or rewrite it.

- ❌ "Built with you in mind." — could describe anything.
- ❌ "Everything you need, all in one place." — anything.
- ✅ "Check the same name across 80+ services at once." — only makes sense here.
- ✅ "Some sites block automated checks. We give you the direct link instead." — specific, believable.

## Rules

- **Say the useful thing immediately.** Not "Unlock smarter brand
  discovery" — "Check where a name is already used."
- **No fake enthusiasm.** Banned words: seamless(ly), effortless(ly),
  powerful, revolutionary, game-changing, cutting-edge, robust,
  supercharge, next-level, unlock, unleash, elevate, empower, transform,
  one-stop, "in today's digital world," "your journey."
- **Don't explain obvious UI.** Not "Enter your name below to begin your
  journey" — just label the field.
- **Concrete over claims.** Not "search across numerous platforms" —
  "check domains, social handles, app stores, packages, and more."
- **Break the section rhythm.** Not every block needs a title, a
  paragraph, and three cards. Some sections need one sentence. Some need
  a table. Some need nothing but the data.
- **Natural headings.** Not "Why Choose Us?" or "Everything You Need" —
  "What we check," "How results are ranked."
- **Simple beats exhaustive.** "This looks available, but we couldn't
  verify it automatically" beats "While this appears to be available, we
  recommend manually verifying its availability to ensure accuracy."
- **Contractions, naturally.** "We don't store your searches," not "We
  do not store your search queries."
- **Don't repeat the product name.** Once the user knows where they are,
  talk normally instead of "NameVetta helps... NameVetta allows..."
- **No em dashes.** Use a period, comma, or parentheses instead.
- **Don't oversell certainty.** "Likely available," "Couldn't verify,"
  "Manual check needed" — not confident language the evidence doesn't
  support.
- **Avoid "whether you're X, Y, or Z"** and **"from X to Y"** marketing
  constructions unless genuinely the clearest way to say the thing.
- **No rhetorical questions as headings.**
- **Never claim instant, accurate, secure, private, or comprehensive**
  unless the implementation actually supports the claim.
- **Buttons describe the actual action.** "Run Quick Check," not
  "Get Started."
- **Error messages say what happened and what to do next.**
- **Empty states are short and useful**, not decorative.

## Keep some personality

Obsessively terse copy reads as machine-generated too. A little casual
language, "We couldn't check this one," "Looks clear so far," makes the
interface feel like a person is behind it. The goal is specific and
plain, not clinical.

## Scope

This applies to everything a user reads: page copy, component text,
`src/lib/presentation.ts`, evidence strings generated by source
adapters, error messages, and metadata descriptions. It does not apply
to code comments, JSDoc, or test descriptions — those are for the next
engineer, not the user.

Before finishing any page or component with new user-facing text, reread
everything visible and remove anything that fails the test above.
